## 1. TurboQuant는 실제로 무엇인가

### 1.1 뉴스가 말하는 것 vs 실제

뉴스 스크립트에서 "메모리 병목을 뚫는 차세대 알고리즘"이라고 소개했지만, 실제로 TurboQuant를 정확히 이해하려면 **세 개의 논문**을 함께 봐야 한다:

| 알고리즘 | 학회 | 핵심 역할 |
|---|---|---|
| **QJL** (Quantized Johnson-Lindenstrauss) | AAAI 2025 | 1비트 양자화 + 비편향 내적 추정기 |
| **PolarQuant** | AISTATS 2026 | 랜덤 회전 + 극좌표 변환으로 정규화 오버헤드 제거 |
| **TurboQuant** | ICLR 2026 | PolarQuant + QJL 결합, 정보이론 한계에 근접하는 최적 양자화 |

TurboQuant는 독립된 하나의 기술이 아니라, **QJL과 PolarQuant를 결합한 2단계 프레임워크**다.

### 1.2 뉴스 스크립트의 부정확한 부분

| 뉴스 설명 | 실제 |
|---|---|
| "입력 데이터를 무작위로 회전시킨 뒤 각 요소를 개별 양자화" | 맞지만, 핵심은 회전이 **Beta 분포를 유도**해서 좌표가 거의 독립이 된다는 것. 단순 회전이 아니라 정보이론적으로 최적화된 스칼라 양자화가 가능해지는 구조적 이유가 있음 |
| "소수점 데이터를 정수로 근사" | 과도하게 단순화. TurboQuant는 MSE 최적 스칼라 양자화 + QJL 잔차 보정의 2단계 구조이며, outlier 채널에 차등 비트 할당까지 포함 |
| "QJL 기법으로 -1, 1 값으로만 표현" | QJL은 2단계 잔차 보정용이지 전체가 1비트라는 의미가 아님. 전체는 3~4비트이며, 그 중 1비트만 QJL |
| "최대 6배까지 메모리를 줄이면서도 성능 유지" | 정확. 3.5비트에서 완전 무손실(quality neutral), 2.5비트에서 미미한 품질 저하. H100에서 최대 8배 어텐션 속도 향상 |

## 2. 기술 딥다이브

### 2.1 왜 KV 캐시가 병목인가

트랜스포머 모델의 어텐션 연산:

```
Attention(Q, K, V) = softmax(QK^T / √d) · V
```

추론(inference) 시 이전 토큰들의 K, V 벡터를 **캐시에 저장**해야 다음 토큰을 생성할 수 있다.

**문제**: 컨텍스트 길이 × 레이어 수 × 헤드 수 × 헤드 차원 × 2(K+V) × 데이터 타입 크기

예시 — Llama-3.1-8B, 128K 컨텍스트:
- 32 레이어 × 8 KV 헤드 × 128 차원 × 128,000 토큰 × 2(K+V) × 2바이트(FP16)
- ≈ **16.8 GB** (KV 캐시만으로)

모델 가중치(~16GB) + KV 캐시(~17GB) = **33GB+** → H100 80GB에서도 배치 크기가 심각하게 제한된다.

**핵심**: TurboQuant는 **모델 가중치 양자화가 아니라 KV 캐시 양자화**에 초점. 이 구분이 중요하다.

### 2.2 기존 양자화 기법과의 결정적 차이

#### 모델 가중치 양자화 (GPTQ, AWQ, GGUF)

이것들은 **모델의 파라미터(가중치)**를 압축한다:
- **GPTQ**: 학습 데이터 의존적, 오프라인 캘리브레이션 필요, 가중치를 4비트로 양자화
- **AWQ**: 활성화 인식 가중치 양자화, 중요한 채널을 보존
- **GGUF**: CPU/GPU 하이브리드 추론용 포맷, 다양한 비트폭 지원

이들의 공통 특성:
- **오프라인 처리**: 사전에 모델을 양자화해서 저장
- **데이터 의존적**: 캘리브레이션 데이터셋 필요
- **정적**: 한번 양자화하면 그 상태로 고정

#### TurboQuant (KV 캐시 양자화)

- **온라인(실시간) 처리**: 추론 중 동적으로 KV 벡터를 압축
- **데이터 비의존적 (data-oblivious)**: 캘리브레이션 불필요, 어떤 데이터가 들어와도 동일한 양자화 규칙 적용
- **이론적 보장**: Shannon 정보이론 한계의 ~2.7배 내로 수렴하는 수학적 증명 존재

| 특성 | GPTQ/AWQ/GGUF | TurboQuant |
|---|---|---|
| 대상 | 모델 가중치 | KV 캐시 (추론 중간값) |
| 타이밍 | 오프라인 (사전 처리) | 온라인 (추론 중 실시간) |
| 캘리브레이션 | 필요 (데이터 의존) | 불필요 (data-oblivious) |
| 이론적 보장 | 경험적 성능 위주 | 정보이론적 최적성 증명 |
| 학습/파인튜닝 | 불필요 | 불필요 |
| 적용 범위 | 모든 파라미터 | KV 캐시 + 벡터 검색 |

**중요**: 이 둘은 경쟁이 아니라 **보완 관계**다. GPTQ로 가중치를 4비트로 줄이고 + TurboQuant로 KV 캐시를 3비트로 줄이면 동시 적용 가능.

### 2.3 TurboQuant 2단계 알고리즘 상세

#### Stage 1: PolarQuant — 고품질 MSE 양자화

**핵심 아이디어**: 랜덤 직교 회전으로 벡터 좌표의 분포를 변환

1. **랜덤 회전 적용**: 입력 벡터 x ∈ ℝ^d에 랜덤 직교 행렬 Π를 곱한다
   - y = Π · x
   - 이 회전은 벡터의 노름과 내적을 **완벽하게 보존** (직교 변환)
   
2. **Beta 분포 유도**: 고차원에서 랜덤 회전 후 각 좌표 y_i는 **집중된 Beta 분포**를 따르게 된다
   - 핵심: 좌표들이 **거의 독립** (near-independent)이 됨
   - 이것이 왜 중요한가? → 다차원 벡터 양자화 문제가 **독립적인 1D 스칼라 양자화 문제들**로 분해됨
   
3. **최적 스칼라 양자화**: 각 좌표에 대해 Max-Lloyd 알고리즘으로 1D 최적 양자화 수행
   - Beta 분포의 형태가 알려져 있으므로, 최적 양자화 코드북을 **사전에 계산** 가능
   - 온라인 추론 시에는 look-up만 하면 됨 → 극도로 빠름

4. **극좌표 변환 (PolarQuant 이름의 유래)**:
   - 좌표를 2개씩 묶어 극좌표 (r, θ)로 변환
   - 반지름(r)을 다시 2개씩 묶어 재귀적으로 극좌표 변환
   - 최종: 하나의 최종 반지름 + 여러 각도(angle)들
   - **장점**: 각도 분포가 알려진 형태라서 정규화(normalization) 오버헤드 제거 — 전통적 양자화에서 1~2비트를 잡아먹던 정규화 상수 저장이 불필요

#### Stage 2: QJL — 1비트 잔차 보정

**왜 필요한가**: Stage 1의 MSE 최적 양자화는 L2 거리는 잘 보존하지만, **내적(dot product) 추정에 bias가 생긴다**.

고차원에서 1비트 MSE 최적 양자화의 내적 편향: **2/π ≈ 0.637** 배의 곱셈 편향

어텐션 연산은 Q·K 내적이 핵심이므로, 이 편향은 어텐션 가중치를 왜곡시킨다.

**QJL의 해결 방식**:
1. Stage 1의 잔차(residual) 계산: e = x - x̂ (원본 - Stage 1 복원값)
2. JL 랜덤 프로젝션 + sign 비트만 저장: b = sign(A · e), A ∈ ℝ^{m×d}
3. 비편향 내적 추정기 구성:
   - ⟨q, x⟩ = ⟨q, x̂⟩ + ⟨q, e⟩
   - 첫 항: Stage 1 양자화값으로 직접 계산 (고정밀)
   - 둘째 항: QJL 1비트 코드로 **비편향 추정** (E[추정값] = 실제값)

**전체 비트 할당**:
- b비트 TurboQuant = (b-1)비트 PolarQuant(Stage 1) + 1비트 QJL(Stage 2)
- 예: 4비트 = 3비트 PolarQuant + 1비트 QJL

#### Outlier 처리 전략

비정수 비트폭(2.5, 3.5비트 등) 구현:
- **Outlier 채널**: 값 분산이 큰 채널에 높은 비트(예: 3비트) 할당
- **Non-outlier 채널**: 낮은 비트(예: 2비트) 할당
- 평균: 2.5비트 달성

이것은 AWQ의 활성화 인식 전략과 유사하지만, TurboQuant는 캘리브레이션 없이 **통계적 기준**으로 outlier를 판별한다.

### 2.4 수학적 보장 — 왜 "near-optimal"이라고 할 수 있나

TurboQuant 논문의 가장 강력한 기여는 **정보이론적 하한(lower bound) 증명**이다.

Shannon의 Source Coding Theory + Yao의 minimax 원리를 결합해서, **어떤 양자화 알고리즘이라도** 달성할 수 없는 최소 왜곡(distortion)을 증명했다.

| 비트폭 | TurboQuant MSE 왜곡 | 정보이론 하한 | 비율 |
|---|---|---|---|
| 1비트 | 0.36 | 0.25 | 1.44× |
| 2비트 | 0.117 | 0.0625 | 1.87× |
| 3비트 | 0.03 | 0.0156 | 1.92× |
| 4비트 | 0.009 | 0.0039 | 2.31× |

**해석**: TurboQuant의 왜곡은 이론적 최소치의 최대 약 2.7배 이내. 이론적 하한은 **어떤 알고리즘도 이보다 나을 수 없는** 절대적 한계이므로, TurboQuant는 실질적으로 최적에 가깝다.

### 2.5 실험 결과 정리

#### KV 캐시 벤치마크 (Llama-3.1-8B-Instruct, Ministral-7B-Instruct)

| 벤치마크 | 원본 FP16 | TurboQuant 3.5비트 | TurboQuant 2.5비트 |
|---|---|---|---|
| LongBench 종합 | 기준 | ≈ 동등 (quality neutral) | 미미한 저하 |
| Needle-in-Haystack (104K) | 100% | 100% | — |
| ZeroSCROLLS | 기준 | ≈ 동등 | — |
| RULER | 기준 | ≈ 동등 | — |

#### 속도 벤치마크 (H100 GPU)

- 4비트 TurboQuant: 어텐션 로짓 계산 **최대 8배 속도 향상** (32비트 대비)
- JAX 최적화 베이스라인 대비에서도 유의미한 개선

#### 벡터 검색 인덱싱 시간

| 방법 | d=200 | d=1536 | d=3072 |
|---|---|---|---|
| Product Quantization | 37.04s | 239.75s | 494.42s |
| TurboQuant | 0.0007s | 0.0013s | 0.0021s |

**PQ 대비 인덱싱 시간이 ~200,000배 빠르다.** data-oblivious 특성 덕분에 k-means 학습 단계가 완전히 제거되기 때문.

## 3. 실제 구현 상태

### 3.1 pip 패키지 이미 존재

```bash
pip install turboquant  # v0.2.0 (2026-03-29 기준)
```

HuggingFace 모델에 바로 적용 가능:
```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from turboquant import TurboQuantCache

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-3B-Instruct", 
    dtype=torch.float16, 
    device_map="auto"
)

# KV 캐시를 4비트로 압축 — 이 한 줄이 전부
cache = TurboQuantCache(bits=4)
outputs = model.generate(..., past_key_values=cache)
```

### 3.2 vLLM 플러그인

```bash
pip install turboquant-vllm  # v1.1.1
```

논문 공개 72시간 만에 vLLM 통합 플러그인이 나왔다. 프로덕션 서빙에 바로 적용 가능.

### 3.3 직접 벡터 양자화 API

```python
from turboquant import TurboQuantMSE

tq = TurboQuantMSE(dim=128, bits=4, device='cuda')
indices, norms = tq.quantize(vectors)        # 양자화
vectors_hat = tq.dequantize(indices, norms)  # 복원
```

## 4. 반도체 시장 영향 분석

### 4.1 주가 반응 (사실 정리)

| 종목 | 3/26 (공개 이틀 후) | 3/27 | 누적 |
|---|---|---|---|
| 삼성전자 | -4.71% | -3.8% | 약 -8.5% |
| SK하이닉스 | -6.23% | -3.9% | 약 -10.1% |
| 코스피 | -3%+ | -3%+ | — |

### 4.2 시장이 왜 놀랐나

**표면적 논리**: "같은 모델 구동에 메모리가 6분의 1만 필요" → HBM/DRAM 수요 급감 → 삼성/하이닉스 매출 타격

**하지만 이 논리는 몇 가지를 간과한다**:

1. **KV 캐시 ≠ 전체 메모리 사용량**
   - TurboQuant는 KV 캐시만 압축한다
   - 모델 가중치, 활성화 텐서, 옵티마이저 상태 등은 영향 없음
   - KAIST 유회준 교수: "KV캐시를 줄인다고 HBM 사용량이 줄지는 않을 것"

2. **KV 캐시의 비중은 컨텍스트 길이에 따라 달라진다**
   - 짧은 컨텍스트(~4K): 모델 가중치가 지배적, KV 캐시 비중 낮음
   - 긴 컨텍스트(128K+): KV 캐시가 전체 메모리의 50% 이상 차지
   - **즉, TurboQuant의 영향은 "긴 컨텍스트 추론"에 집중됨**

3. **학습(Training)에는 영향 없음**
   - TurboQuant는 추론(Inference) 전용 기술
   - GPU/HBM 수요의 상당 부분은 학습에서 발생
   - 학습 수요는 계속 증가 중

### 4.3 제번스 역설 (Jevons Paradox) 분석

헤럴드 경제가 정확하게 짚었다:

> 기술 발전으로 효율성이 높아지면 자원 비용이 하락하면서 오히려 전체 사용량이 증가하는 현상

**역사적 사례**:
- 제임스 와트의 증기기관 → 석탄 효율 ↑ → 석탄 사용 장벽 ↓ → 총 석탄 소비 ↑
- LED 조명 → 전기 효율 ↑ → 조명을 더 많은 곳에 설치 → 총 조명 전력 ↑
- 클라우드 컴퓨팅 → 서버 효율 ↑ → 컴퓨팅 접근성 ↑ → 총 서버 수요 ↑

**TurboQuant 적용**:
- KV 캐시 6배 압축 → 같은 GPU에서 6배 긴 컨텍스트 or 6배 많은 동시 요청
- AI 추론 비용 ↓ → AI 도입 장벽 ↓ → 더 많은 기업/서비스가 AI 사용
- 결과: **개별 요청당 메모리 ↓, 총 요청 수 ↑↑ → 총 메모리 수요 ↑**

KB증권 분석: "저비용 AI 기술은 AI 사용장벽을 낮춰 전체 수요를 폭발적으로 확대시키며, 최대 수혜는 메모리 반도체 업체가 될 것"

### 4.4 판단

**단기** (1~3개월): 센티먼트 쇼크로 주가 조정. "AI = 메모리"라는 단순 공식에 금이 갔다는 심리적 충격.

**중기** (6~12개월): 실질 영향은 제한적. TurboQuant가 영향을 미치는 건 KV 캐시뿐이고, 상용화 시간도 필요.

**장기** (1~3년): 제번스 역설 작동. AI 효율화 → 대중화 → 총 수요 증가. 다만 수요의 **질**이 변한다:
- "대용량 일변도" → "고대역폭 + 저전력 + 효율 최적화"
- HBM의 경쟁 축이 "용량"에서 "대역폭/와트" 쪽으로 이동할 가능성

## 5. 더 넓은 AI 효율화 흐름에서의 위치

### 5.1 "효율화 혁명"의 지도

TurboQuant는 고립된 사건이 아니라, AI 효율화의 큰 흐름 안에 있다:

| 시기 | 사건 | 영향 |
|---|---|---|
| 2024.06 | QJL 논문 (AAAI 2025 발표) | 1비트 JL 변환으로 KV 캐시 5배 압축 |
| 2025.01 | DeepSeek R1 | "소규모 팀 + 효율적 학습"으로 대형 모델 성능 달성, 시장 충격 |
| 2025.02 | PolarQuant 논문 (AISTATS 2026 발표) | 극좌표 변환으로 정규화 오버헤드 제거 |
| 2025.09 | Llama 3.2 경량화 | 1B/3B 모델이 모바일에서 구동 |
| 2026.03 | TurboQuant (ICLR 2026) | QJL + PolarQuant 통합, 정보이론적 최적성 증명 |

공통 방향: **"더 큰 모델"에서 "같은 성능을 더 적은 자원으로"**

### 5.2 경쟁/관련 기법들과 비교

| 기법 | 대상 | 비트폭 | 캘리브레이션 | 정확도 손실 |
|---|---|---|---|---|
| GPTQ | 모델 가중치 | 4비트 | 필요 | 미미 |
| AWQ | 모델 가중치 | 4비트 | 필요 | 미미 |
| KIVI | KV 캐시 | 2비트(K)+4비트(V) | 필요 | 소량 |
| KVQuant | KV 캐시 | 3-4비트 | 필요 | 소량 |
| **TurboQuant** | **KV 캐시 + 벡터검색** | **2.5-4비트** | **불필요** | **3.5비트에서 0** |

TurboQuant의 차별점:
1. **data-oblivious** — 캘리브레이션 없이 바로 적용
2. **이론적 최적성 증명** — 다른 기법들은 경험적 성능만 보고
3. **KV 캐시 + 벡터 검색 이중 적용** — 범용성
4. **인덱싱 시간 거의 0** — PQ 대비 20만배 빠름

### 5.3 한계와 미해결 질문

1. **모델 가중치에는 적용 안 됨**: KV 캐시 전용. 가중치 양자화는 별도 기법 필요
2. **학습에 적용 불가**: 추론(inference) 전용
3. **매우 긴 컨텍스트에서의 노이즈 누적**: 100K+ 토큰에서 초기 토큰 정보가 양자화 노이즈에 묻히는지? → Needle-in-Haystack 104K에서 100% 유지했으므로 현재 벤치마크에서는 문제 없음
4. **멀티모달 KV 캐시**: 이미지/비디오 토큰의 KV 캐시에도 동일 효과? → 논문에서 다루지 않음
5. **수학/코딩 등 정밀 추론 태스크**: LongBench 외 GSM8K, HumanEval 등에서의 검증? → 추가 실험 필요
6. **실제 프로덕션 GPU 사용량 감소 정도**: 벤치마크 vs 실사용 간 괴리 가능

## 6. 우리 작업에 대한 시사점

### 6.1 CoinPilot 직접 영향

CoinPilot의 ML 모델(XGBoost/LightGBM 앙상블)에는 **직접적 영향 없음**:
- 트리 기반 모델은 트랜스포머가 아님
- KV 캐시 개념 자체가 없음
- 모델 크기가 수 MB 수준으로 양자화 필요성 없음

### 6.2 간접적 영향 — API 비용과 가용성

1. **Gemini API 비용 감소 가능**: 구글이 TurboQuant를 Gemini에 적용하면 추론 비용 감소 → API 가격 인하 가능
   - 우리가 Gemini 503 에러와 씨름했던 것, 비용 때문에 호출을 제한했던 것이 완화될 수 있음
   
2. **긴 컨텍스트 실용화**: KV 캐시 6배 압축 → 128K+ 컨텍스트가 비용 효율적
   - 종합 시장 분석 보고서, 장기 트레이딩 히스토리 분석 등에 대형 LLM 활용 가능성 ↑
   
3. **온디바이스 AI**: 효율화가 계속되면 모바일에서 의미 있는 크기의 모델 구동 가능
   - CoinPilot 프론트엔드에서 간단한 ML 추론 가능성 (먼 미래)

### 6.3 투자/시장 관점

CoinPilot이 암호화폐 자동매매를 하는 만큼, 이런 기술 이벤트의 시장 영향 패턴을 이해하는 건 가치가 있다:

**패턴**: "효율화 기술 발표 → 관련 하드웨어 주가 급락 → 실제 영향 제한적 → 반등"
- DeepSeek R1 (2025.01): NVIDIA 주가 -17% → 이후 회복
- TurboQuant (2026.03): 삼성전자 -8.5%, SK하이닉스 -10.1% → ?

이런 패턴은 시장의 **과잉 반응(overreaction)** 사례로, 기술의 실제 영향 범위를 정확히 이해하면 투자 기회가 될 수 있음.

### 6.4 기술 학습 관점

TurboQuant에서 배울 수 있는 **범용적 기술 원리**:
1. **정보이론적 한계 인식**: "이론적으로 불가능한 것"을 알면 불필요한 시도를 줄일 수 있다
2. **Data-oblivious 설계의 가치**: 캘리브레이션 없이 작동하는 시스템이 프로덕션에서 훨씬 강건
3. **잔차 보정 패턴**: Stage 1 양자화 → Stage 2 잔차 보정은 다양한 문제에 적용 가능한 일반 패턴
4. **Johnson-Lindenstrauss 정리의 실용성**: 고차원 → 저차원 축소에서 거리 보존이 가능하다는 수학적 보장, 이것이 실제 시스템에 적용될 수 있음을 보여줌

## 7. 핵심 정리

### 한 문장 요약
TurboQuant는 "LLM 추론 시 KV 캐시를 정보이론적 최적에 근접하게 3~4비트로 압축하는, 캘리브레이션 불필요한 온라인 양자화 알고리즘"이다.

### 가장 중요한 5가지

1. **모델 가중치가 아니라 KV 캐시 양자화** — 대부분의 뉴스가 이 구분을 명확히 하지 않음
2. **data-oblivious** — 캘리브레이션 없이 어떤 모델/데이터에나 즉시 적용 가능한 것이 실전 가치의 핵심
3. **정보이론 한계의 ~2.7배 내** — "이보다 나은 양자화는 수학적으로 불가능"에 근접
4. **이미 pip install 가능** — 연구실 기술이 아니라 바로 쓸 수 있는 상태
5. **반도체 시장 영향은 제번스 역설** — 단기 충격, 장기 수요 증가가 대다수 전문가 전망

### 뉴스 vs 실제의 가장 큰 괴리

뉴스: "메모리 6배 줄인다 → 반도체 죽는다"
실제: "KV 캐시만 6배 줄인다 → 긴 컨텍스트가 실용화된다 → AI 더 많이 쓴다 → 총 수요 늘 가능성 높음"

## 8. 자체 검증 실험 결과 (2026-03-29)

### 8.1 실험 환경

- GPU: NVIDIA RTX 4070 Ti SUPER (16GB VRAM)
- PyTorch 2.11.0+cu126, Transformers 5.4.0, turboquant 0.2.0
- 모델: Qwen2.5-3B-Instruct (FP16, ~5.9GB VRAM)
- 비교: FP16 KV 캐시 vs TurboQuant 4비트 vs TurboQuant 3비트
- 테스트: 한국어, 수학, 논리, 컨텍스트 검색, 코드 생성 6개

### 8.2 결과 요약

| 테스트 | FP16 (기준) | TQ 4비트 | TQ 3비트 |
|---|---|---|---|
| kr_1 (한국어) | ✅ 29.1 tok/s | ✅ 29.3 tok/s | ✅ 30.1 tok/s |
| num_1 (나눗셈) | ✅ 32.3 tok/s | ⚠️ 20.8 tok/s | ⚠️ 21.0 tok/s |
| num_2 (복리계산) | ✅ 31.2 tok/s | ❌ reshape 에러 | ❌ reshape 에러 |
| logic_1 (추론) | ✅ 32.5 tok/s | ❌ reshape 에러 | ❌ reshape 에러 |
| ctx_1 (검색) | ✅ 31.8 tok/s | ⚠️ 20.0 tok/s | ⚠️ 20.0 tok/s |
| code_1 (코드) | ✅ 32.2 tok/s | ❌ reshape 에러 | ❌ reshape 에러 |

### 8.3 발견사항 — 논문과 현실의 괴리

#### 발견 1: pip 패키지 v0.2.0에 버그 존재

"cannot reshape tensor of 0 elements" 에러가 **긴 생성(100+ 토큰)**에서 발생. 6개 테스트 중 3개 실패(50%). 이건 cache reset 후 재사용 시 텐서 형상 불일치 문제로, **프로덕션에서 바로 쓸 수 없는 상태**.

#### 발견 2: 출력 품질 저하 확인

TurboQuant가 성공한 테스트에서도 문제가 있었음:

- **num_1 (나눗셈)**: FP16은 정확한 계산과정 포함 → TQ 4비트는 **이전 응답의 잔여 출력**이 섞임 ("이고, 연산량도 감소시킵니다" — kr_1 응답의 일부)
- **ctx_1 (컨텍스트 검색)**: FP16은 **정확하게** 78%, 50만 스택을 찾음 → TQ 4비트/3비트 모두 **"정보가 제공되지 않았습니다"**라고 틀린 답변. 컨텍스트에 명확히 있는 정보를 찾지 못함
- **kr_1 (한국어)**: FP16과 TQ 모두 동일한 응답 (이건 유일하게 정상 작동)

#### 발견 3: 속도 저하 (단기 시퀀스)

FP16: ~31-32 tok/s → TurboQuant: ~20-21 tok/s (**35% 느림**)

논문의 "8배 speedup"은 **매우 긴 시퀀스(수만 토큰)**에서의 어텐션 연산 기준. 짧은 시퀀스에서는 양자화/역양자화 오버헤드가 지배적이라 오히려 느려짐.

#### 발견 4: 메모리 절감 미미 (짧은 컨텍스트)

| 설정 | Peak VRAM (평균) |
|---|---|
| FP16 | ~5,920 MB |
| TQ 4비트 | ~5,922 MB |
| TQ 3비트 | ~5,952 MB |

차이가 거의 없음. 이유: 3B 모델의 가중치(5,886 MB)가 전체 VRAM의 99%를 차지하고, 짧은 시퀀스의 KV 캐시는 수 MB에 불과. KV 캐시 절감이 의미 있으려면 **수천~수만 토큰 컨텍스트**가 필요.

### 8.4 결론

| 논문 주장 | 우리 검증 결과 | 판단 |
|---|---|---|
| "zero accuracy loss" | num_1/ctx_1에서 품질 저하, ctx_1에서 정답 실패 | **pip 구현에서는 미달성** |
| "6x memory reduction" | 짧은 시퀀스에서 차이 없음 | **긴 시퀀스 테스트 필요** |
| "8x speedup" | 오히려 35% 느려짐 | **짧은 시퀀스에서는 역효과** |
| "pip install로 바로 사용" | 6개 중 3개 에러, 품질 저하 | **v0.2.0은 프로덕션 미적합** |
| "data-oblivious" | 캘리브레이션 없이 적용은 맞음 | **원리는 맞지만 구현이 미성숙** |

### 8.5 시사점

1. **논문의 알고리즘 자체는 탄탄** — 정보이론적 증명이 있고, 구글 내부 벤치마크(ICLR 2026)에서 검증됨
2. **pip 패키지 v0.2.0은 아직 초기** — reshape 버그, 이전 응답 잔류, 컨텍스트 검색 실패 등
3. **적용 영역이 명확** — 수만 토큰 긴 컨텍스트 추론에서만 의미 있음. 짧은 대화에서는 역효과
4. **"바로 쓸 수 있다"는 과장** — 원리는 data-oblivious이지만, 구현 품질이 따라오지 못함
5. **10%의 여백이 작동** — 논문만 읽었으면 "완벽하다"고 생각했을 것. 직접 돌려봐서 현실을 확인

> 결론: 터보퀀트의 **이론적 가치**는 확실하다. 하지만 **실전 적용**은 구현 성숙도가 올라올 때까지 기다려야 한다. 특히 pip 패키지 v0.2.0은 프로덕션에 부적합하며, 긴 컨텍스트 벤치마크를 포함한 추가 검증이 필요하다.
